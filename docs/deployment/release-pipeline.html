← → step · Space plays
ci
Authoritative Lockfile Policy → Secure Install Review → Prepare Dependency Cache → Chromatic + Setup Affected Context → Lint + Test → Build Backend / Build Frontend (ci.yml). Which target ran on which project, and why a red one blocks in one mode and only reports in another, is docs/sandcastle/gates.html and ADR 0012 — this page treats the whole thing as one pass/fail box on purpose.
staging
workflow_run on CI completing with conclusion == 'success' on main (deploy-staging.yml:4-7, :18). Fully automatic, and it never leads anywhere near production — the backend path is identical to production's, the frontend path is not. See panel 2.
cut
The one human choice on this whole spine before the halt: when to run it. release:cut checks out main, confirms it is clean and up to date, and creates + pushes release/vX.Y.Z (package.json:27, release.mjs:541, :571-576). It has no --tag flag — cutting cannot tag.
releasepr
Fires on push to release/v* (release-pr.yml:4-6). Opens or reuses a PR to main and tries to enable auto-merge (:103-115). Simultaneous with, and independent of, the production dispatch below — the same push causes both.
dispatch
Fires on create of a branch matching ^release/v[0-9]+\.[0-9]+\.[0-9]+$ (dispatch-production-deploy.yml:5, :17). It calls createWorkflowDispatch against deploy-production.yml (:91-99) and nothing else — its own job never runs a deploy step. Its previous name, Deploy Production (latest release), read as though it did; that misreading is why it was renamed (ADR 0028, Consequences). No step in this chain, or in the workflow it dispatches, checks whether CI is green on the branch it just created.
prodstart
The workflow file is literally named Deploy Production (manual) (deploy-production.yml:1) and its only trigger is workflow_dispatch (:3-4) — a workflow just dispatched it automatically, one node back. The word “manual” in the name describes the approval gate two steps ahead, not how the run started.
validate
Rejects any github.ref that is not refs/heads/release/* (deploy-production.yml:36-43) — that guard accepts release/anything, not only semver. Timeout 5 minutes (:22). Then resolves release_ref: the explicit release_branch input if that branch exists on origin (:54-61), otherwise the newest release/vX.Y.Z by sort -V (:66-70). Panel 3 has the full asymmetry between this ref and the one each job actually checks out.
offrepo
The single thing that makes this workflow manual: the production GitHub Environment's required-reviewer rule. It lives in repository settings, not in any file this diagram — or git grep — can show you. Every workflow file reads exactly the same with or without it, and it is removable without a pull request (ADR 0028). Verify it directly: gh api repos/mnaimfaizy/myorganizer/environments/production --jq '.protection_rules'.
halt
deploy-backend (deploy-production.yml:121) and deploy-frontend (:170) both declare environment: production. Everything upstream of this box happened without anyone deciding anything; everything downstream needs the sign-off this box represents. Choose an outcome below to continue the walkthrough.
deploybackend
Packages with yarn package:backend:api and ships ./dist/deploy/backend-api/ over FTP to cPanel, using a production backend FTP credential distinct from staging's (deploy-production.yml:152-163). Timeout 45 minutes (:120), FTP transfer timeout 300000 ms — the same figure staging and the frontend job both use.
deployfrontend
Packages with yarn package:myorganizer:web and ships ./dist/deploy/myorganizer-web/ over FTP to cPanel (deploy-production.yml:221-232). Production never invokes Vercel; staging's frontend does. That is the one place the two environments genuinely diverge — see panel 2.
tag
Asserts it is on the release branch and up to date with origin, and that package.json matches the tag (release.mjs:684-686); refuses an existing tag (:688-690); creates no commit and writes no files (package.json:28). A commit here would move the branch past the exact SHA CI verified and a reviewer approved. vX.Y.Z existing means that version reached production.
publish
Triggered by the push of a tag matching ^v[0-9]+\.[0-9]+\.[0-9]+$ (publish-github-release.yml:4-6, :35). Reads RELEASE_NOTES.md from the tagged commit and creates or updates the GitHub Release, so re-running it is safe (:79-100).

1 · The trigger chain

what starts what, in order
# Trigger Fires Citation
1 push/PR to main or release/** CI ci.yml:3-12
2 CI completed on main, conclusion == 'success' Deploy Staging deploy-staging.yml:4-7, :18
3 yarn release:cut --version vX.Y.Z --push creates + pushes release/vX.Y.Z package.json:27, release.mjs:541, :571-576
4a push to release/v* Release PR (auto) → PR to main, tries auto-merge release-pr.yml:4-6, :103-115
4b create of release/vX.Y.Z Dispatch Production Deploy → dispatches the deploy dispatch-production-deploy.yml:5, :17, :91-99
5 workflow_dispatch (by 4b or a person) Deploy Production (manual) — halts at approval deploy-production.yml:3-4, :121, :170
6 yarn release:tag --version vX.Y.Z --push annotated tag, no commit, no files package.json:28, release.mjs:684-691
7 push of a v*.*.* tag Publish GitHub Release (idempotent) publish-github-release.yml:4-6, :79-100

Rows 4a and 4b are simultaneous consequences of one push, not a sequence — the hero draws them as a fork for that reason.

2 · Staging is not a rehearsal of production

the two environments do not have the same shape

The backend path is identical on both. The frontend path is not — a production frontend deploy exercises FTP-to-cPanel code that a staging run never touches, and a staging frontend deploy exercises Vercel CLI code production never touches.

3 · Which ref actually ships

deploy-production.yml

The branch you launch the run from and the branch that deploys can differ. Rendered as written, not editorialised.

  1. validate rejects any github.ref that is not refs/heads/release/* — note this guard accepts release/anything, not only semver. :36-43
  2. It resolves release_ref: the explicit release_branch input if that branch exists on origin :54-61, otherwise the newest release/vX.Y.Z by sort -V :66-70.
  3. The three job guards (prepare-dependencies, deploy-backend, deploy-frontend) test github.ref :81, :117, :166 — the ref the run was launched against.
  4. The deploy jobs check out release_ref :92, :128, :177 — the resolved branch from step 2, which is not always the same string.

4 · The tag is a receipt

release.mjs

release:tag asserts it is on the release branch, up to date with origin, and that package.json matches the tag (release.mjs:684-686); refuses an existing tag (:688-690); and creates no commits and writes no files — a commit here would move the branch past the exact SHA that CI verified and a reviewer approved (:670-676). release:cut has no way to tag at all: there is no --tag flag. vX.Y.Z existing means that version reached production (ADR 0028). That is why tagging comes last, not first.

5 · Constants, with their scopes

collision check, run repo-wide
Node — three scopes, one floor

CI runners pin exactly '22' at all 14 setup-node steps across ci.yml, deploy-staging.yml, deploy-production.yml. The repo floor is >=22.0.0 (package.json:7). release.mjs refuses a major below 22 (:11-19). Three scopes, one floor — not a single pinned number.

Vercel CLI

50.1.1, staging frontend deploy only (deploy-staging.yml:158). Production never invokes Vercel. VERCEL_FRONTEND_HOSTING.md:56-66 says vercel@latest — that is human first-time setup, not the pipeline, and the two do not conflict.

FTP transfer timeout

300000 ms, the same value at three sites: staging backend (deploy-staging.yml:103), production backend (deploy-production.yml:163), production frontend (:232).

Job timeouts

validate 5 min (:22); staging jobs 30 min (deploy-staging.yml:21, :58, :109); production deploy jobs 45 min (deploy-production.yml:120, :169); dispatcher, release-PR and publish 10 min each.

Concurrency

deploy-staging sets cancel-in-progress: true — a newer staging run kills the one in flight (:9-11). deploy-production sets false — production runs queue and are never cancelled (deploy-production.yml:11-14).

Four branch/tag patterns, one set

Not the same strictness: refs/heads/release/* (deploy-production.yml:36); ^release/v[0-9]+\.[0-9]+\.[0-9]+$, used twice (dispatch-production-deploy.yml:38, :53, release-pr.yml:34); ^v[0-9]+\.[0-9]+\.[0-9]+$ (publish-github-release.yml:35); and /^v?(\d+)\.(\d+)\.(\d+)$/ (release.mjs:140), which rejects prerelease input outright.

6 · What CI actually is, in dependency order

what “green” means before a deploy · ci.yml
  1. Authoritative Lockfile Policy :22
  2. Secure Install Review :141, needs the above :144
  3. Prepare Dependency Cache :202, needs the above :206
  4. Publish to Chromatic :237 and Setup Affected Context :334, in parallel
  5. Lint :412 and Test :458
  6. Build Backend :648, only when backend is affected :652, and Build Frontend :694, :698

Dependency Review runs on pull requests only (:77, :79). This is context for the word “green,” not a second hero — the gate-tier story belongs to gates.html and ADR 0012.
