Resume

A slice branch with commits on it is resumed, not recreated. This page is about the brief that resumed agent receives: which of the two kinds of prior run it is told it is continuing, which guardrails come with that, what the previous run reported doing, and how much of that can be trusted.

Three git facts pick the disposition. One local tag — and only that tag — picks which of the two briefs gets written.

Reading test

If the slice branch has no wip/<issue>-checkpoint tag, the previous run finished — the agent will be told to verify, not to re-run. The commits are there either way; the tag is the only thing that says how they got there.

What the next agent is told

The disposition is decided from three git facts, and those three facts are the same whether the run crashed or finished cleanly. The split into two kinds happens afterwards, from a local tag, and it is the only thing that changes the wording of the brief.

merge-base(slice, base) === base
The guard on skip-stale. Slices stack — each is cut from the live feature head so it builds on every integrated predecessor — so a checkpoint left behind while later slices integrated is based on a head that is no longer in the feature branch's history. It can neither fast-forward nor be safely built on, and rebasing it is the human's call.
--fresh
The only path that destroys a checkpoint, and the only input here a human types. It is scope-validated before it runs: refused outright in sweep mode, refused outright by the wave driver, and in PRD mode accepted only when it also names its slice — --prd <n> --issue <slice> --fresh. A blanket discard across a PRD is the blast radius resume exists to remove.
decideSliceDisposition()
Pure, and deliberately narrow: it reads branch existence, commits ahead, merge-base, and the discard flag. It does not read the tracker, the log, or the tag. That narrowness is what left the two kinds indistinguishable until a separate probe was added beside it.
fresh
Returned for a branch that does not exist, a branch with nothing ahead of the base, or any branch at all when --fresh was passed. The first two destroy nothing, because there was nothing there. The third is the deliberate act.
skip-stale
Reported and skipped, with the branch left intact. Not rebased — that is a judgement call — and not deleted, because deleting would destroy work the maintainer has not seen. The status:in-progress label comes back off and the run moves to the next slice.
resume
The branch and its commits stay exactly where they are. Only the worktree is removed and rebuilt, so the agent gets a clean checkout of the checkpoint rather than whatever partial state the interrupted container left on disk.
readPriorRun()
Runs only on the resume path, and asks the one question the disposition never asks: is there a wip/<issue>-checkpoint tag, and does it point at the branch head? A tag that exists but has fallen behind the head means work landed after the checkpoint, so it is no longer the interrupted case. The same call also pulls the handoff out of the slice log.
interrupted
The crash path tags what it preserves, and nothing else does. That is the entire signal. Operator output says so too: the orchestrator prints resuming from interrupted run here, where it used to print the same sentence for both kinds.
gate-failure
An untagged head is a head that was committed normally. The run signalled completion, the work went through the Commit sub-agent, and the host build gate is what stopped the slice from integrating. The orchestrator prints resuming from completed run whose gate failed.
How the interrupted commit was made
--no-verify is deliberate: husky must not lint work that was half-written when the run died. The consequence is that no deterministic check has ever seen these files, which is exactly what guardrails 5 and 6 assert — and exactly what makes them false about a run that finished.
How the gate-failure commit was made
Husky ran and passed. The pipelines that slice's gate tier demanded ran and were reviewed. What failed was the host gate, in a container, after the agent was gone — which is a fact about the branch, not about the agent's work.
RESUME_GUARDRAILS_COMMON
The four that hold whatever ended the run, because all four are about review status, not about checks. An agent that did not finish leaves work no reviewer signed off on; so does an agent whose gate went red. RESUME_GUARDRAILS still exists as a deprecated composed view — these four plus the two interrupted ones — so older callers keep working.
INTERRUPTED_GUARDRAILS
Two statements of fact about a Slice Checkpoint. They were unconditional until ADR 0044, and that is what cost issue #447 a quota window.
GATE_FAILURE_GUARDRAILS
The instruction inverts: do not re-run a pipeline whose result the handoff already accounts for; confirm the work exists, then fix what the gate reported. Re-checking is still expected — a green result is confirmation, not new information.

--fresh is scope-validated before it runs

A discard is a surgical instruction about one attempt a maintainer has inspected and judged worthless. Applied to a whole PRD it becomes “destroy any checkpoint you encounter”. So validateDiscardScope refuses it in sweep mode outright, requires --issue <slice> alongside it in PRD mode, and planWaveForwarding refuses to forward it from the wave driver at all — the driver prints the two-command recovery instead of guessing.

The retry loop is not the resume path. maxIterations is 2, and iterations 2..N spin a fresh sandbox, re-run the dependency install, and receive the identical prompt — cold restarts, not continuations. Genuine continuation is resume, which supplies a different prompt. See ADR 0035.

Six guardrails: four shared, two that depend on the kind

resumeGuardrails(kind) tools/scripts/lib/sandcastle-resume.mjs
RESUME_GUARDRAILS_COMMON — 4 rules, in both briefs
  1. The previous run's commits are a starting point, not approved work. Audit them before you extend them.
  2. Do not reset, rebase, or amend those commits. They are the maintainer's anchor for diffing what the previous run produced. Correct them forward with normal commits.
  3. Do not restart from scratch and do not revert files wholesale. If part of the work is wrong, change it forward and say why.
  4. Report your inventory before your first edit: which acceptance criteria are met, which are partial, and which are untouched.
+ INTERRUPTED_GUARDRAILS · interrupted
  1. Files present in the checkpoint do not satisfy a Gated Pipeline. A spec file already in the tree does not mean TestScaffold ran, was reviewed, or passed.
  2. Nothing here has passed a deterministic check. It was committed with --no-verify while the run was being killed, so lint, tsc and the test suite have never once seen it.
+ GATE_FAILURE_GUARDRAILS · gate-failure
  1. The previous run finished and committed through the Commit sub-agent — it was the host build gate that failed, not the agent. Do not re-run a pipeline whose result the handoff already accounts for.
  2. Deterministic checks ran inside that run and the commit passed husky. Re-run them to confirm the current state, but treat a green result as expected rather than as new information.

RESUME_GUARDRAILS is still exported as a deprecated composed view — the 4 common rules plus the 2 interrupted ones, which is what every brief used to get unconditionally. New callers use resumeGuardrails(kind).

What the unconditional wording cost — issue #447

#447's first run finished. It committed through the Commit sub-agent with husky green; the gate then failed on an orchestrator bug, so the slice did not integrate. On the next dispatch it was handed the interrupted brief — false in every clause — believed it, reported back that no pipeline had run and no deterministic check had touched the files, and set out to redo the lot.

ComponentBuilder ComponentReviewer TestScaffold TestReviewer TestRunner /code-review

All six had already cleared that work. The information that would have prevented it is not in git: git records the files a run produced, never which Gated Pipelines ran, whether /code-review passed, or why the run ended. See ADR 0044.

The handoff — what the previous run said it did

The gap ADR 0044 closes is not a git gap somebody forgot to read. No git command reports execution history, so the run has to say so itself, as it goes.

The last run segment
A slice log is appended to across runs, so segmenting it is not a nicety. RUN_START_MARKER is the literal --- Run started:, and extractHandoff takes everything after the last one. Where the log lives, how it is named, and what else is in it are drawn on logs.html.
extractHandoff()
HANDOFF_MARKER is the literal HANDOFF:, and MAX_HANDOFF_LINES caps what travels at 40 so a chatty run cannot flood the brief. Only marker lines travel: a raw log tail would drag a dead agent's mid-thought reasoning into the next brief where a model reads it as instruction. Filtering to a prefix removes that surface entirely.
Markers found
formatHandoffSection puts the epistemics in the brief itself: self-reported by that run as each step completed, so confirm a claim cheaply — the commit exists, the file is in the tree — and then review rather than re-run. Re-run only what these lines do not account for.
No markers
An empty handoff renders nothing. There is no “no markers found” line, because a line like that invites the reading the next note rules out.
Absent means unknown
This is the distinction most likely to be lost. Markers are self-reported, so an agent killed between doing a thing and reporting it leaves that step invisible, not undone. The failure mode is therefore wasted work, never skipped work — the same direction ADR 0035 chose.
Three readings of one handoff formatHandoffSection · ADR 0044
Present — evidence

HANDOFF: TestScaffold → TestReviewer APPROVED → TestRunner 38 passed means that run says it did that. Check the commit and the tree, then review the output. Trust it enough to stop re-running blind.

Absent — unknown

No section in the brief. The agent is told nothing about pipelines and the conservative interrupted wording applies. It re-runs what it cannot account for, which is the correct direction to be wrong in.

Never — proof, or “nothing ran”

These lines mean the work is done and reviewed. No lines mean no pipeline ran. Both readings turn a self-report into authority. The first skips verification; the second re-manufactures the #447 waste from the opposite direction.

  • The diff is deliberately not inlined. The agent can read it from git in one command, and spending the context budget on it defeats the point of resuming rather than restarting. When the file list is unavailable the brief says so and names the command, rather than printing an empty inventory.
  • Maintainer notes wrap the base prompt, so a resumed brief inherits them — a maintainer reviewing a checkpoint is the likeliest author of one. Only text filed under a ## Maintainer Review heading on the Slice Issue travels; the orchestrator's own status comments do not.
  • Rule 4 is the first thing the agent must answer. Which acceptance criteria are met, which are partial, which are untouched — before the first edit.

The slice log is the carrier

The handoff travels in the slice log because the slice log always exists — --trace-subagents is opt-in, so logs/subagents/<n>/index.md may simply not be there, and a channel that is absent by default cannot be the source of truth. Where the evidence lives, and what is missing unless you asked for it, is drawn there.

Parking on a provider limit instead of crashing

classifyRunFailure · decideWaitPolicy tools/scripts/lib/sandcastle-resume.mjs · .sandcastle/main.mts

Quota exhaustion is the expected outcome of dispatching a PRD overnight, and it is the case resume was built for. The thrown agent error is not the input — it carries whatever was last on stderr, routinely a trailing warning rather than the cause. The log tail is. Every gate below must pass, or the run exits with the checkpoint preserved and says why.

  1. --wait-for-quota was passed. Waiting is opt-in: a dispatch that goes silent for hours with no output is a severe surprise, so the behaviour is documented at the call site.
  2. The classification is limit-hit. The other two are other — we looked and it was not a limit — and unknown, which means we did not look. Matchers are per provider: 3 for claude, 0 for cursor, 0 for copilot. A guessed matcher is worse than none, because a wrong guess can trigger a multi-hour sleep.
  3. A reset time was parsed, not guessed. Only the observed resets 4:30am (UTC) shape is accepted; a bare local time would be ambiguous across the machines this runs on. An unreadable timestamp exits.
  4. Fewer than 2 waits have been taken this run (MAX_QUOTA_WAITS).
  5. The reset is within 6 hours — MAX_WAIT_MS = 21600000 ms. A provider's usage window is measured in hours, so a reset further out means something is wrong — a stale message, a truncated line, a changed format — and sleeping on it wastes most of a day.
  6. Sleep until the reset plus a 5-minute margin (300000 ms — waking exactly on the wall risks meeting it again and burning a wait for nothing), then push the slice back into the queue. The next pass finds the checkpoint and resumes. Ctrl-C is safe: the checkpoint is already committed.

The wait window is reported in the operator's own timezone with the duration attached — 21 Aug, 2:30 pm AEST (in 19h 25m) — because a UTC timestamp reads as unremarkable while a duration makes an obviously wrong wait obvious.
