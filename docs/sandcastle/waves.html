Wave Dispatch

What order your PRD's slices will run in, what rewrites your ready-for-agent labels while they do, and what the driver does when a wave does not finish. One page of the five-page sandcastle atlas; the hub is dispatch-map.html.

1orchestrator pass per wave
2label writes per wave
1gate per PRD
3GitHub write points
0pushes

The driver itself never runs an agent and never touches a container. It orders slices, rewrites labels, and calls main.mts once per wave.

The one fact to leave with

A wave is an ordering, not a batch. Each wave is one full main.mts --prd <n> pass, and that pass fast-forwards everything it finishes into the local feature branch — so wave 2 branches off a head that already contains wave 1. The driver no longer stops when a wave comes back incomplete (ADR 0045). It records the wave, runs the rest, gates once, and leaves a summary you read in the morning.

How your slices become waves

fetchSlices · blockersOf · computeWaves
  1. Select. gh issue list against mnaimfaizy/myorganizer, filtered to type:afk, --state all, capped at --limit 100. Of those, the driver keeps the issues whose body contains PRD: #<n>. all and not open is deliberate: the orchestrator closes a slice when it integrates, and a closed slice still has to be visible for blocker resolution and for the completeness check.
  2. Read the edges. Each body is matched for a ## Blocked by section; every #<number> inside it becomes an edge. References that are not themselves slices of this PRD are dropped, and so is a self-reference.
  3. Level it. Kahn's algorithm, level by level: a slice enters the current wave when every one of its blockers is already resolved. Within a wave, slices are sorted ascending by issue number. A level that comes out empty means a cycle or an unsatisfiable blocker, and that ends the run.
The reading test

If your slice has no ## Blocked by section, it lands in wave 1 — check that is what you meant. There is no implicit ordering by issue number, by creation date, or by the order slices appear under the PRD's ## Slices heading. A slice is in wave 1 unless it names a blocker, and that blocker is itself a type:afk slice of the same PRD.

Label rewriting is the dispatch mechanism

gh issue edit · two writes per wave

The driver has no private channel into the orchestrator. It orders waves by mutating the tracker: main.mts dispatches whatever is open and ready-for-agent and type:afk, so making a wave run means making exactly that wave match, and making everything else not match.

What happens to each PRD slice before a wave runs
Slice Already has ready-for-agent Write
In this wave, not done no GH WRITE add ready-for-agent
In this wave, not done yes nothing — the state is already right
Any other PRD slice yes GH WRITE remove ready-for-agent
Any other PRD slice no nothing

“Any other PRD slice” means every other one: a slice in a future wave, and a slice that finished three waves ago. The removal is what stops the orchestrator's open + ready + type:afk filter from re-dispatching work that is already in the branch.

The cost of doing it this way

These writes are not transactional. If a run ends between the adds and the removes — a quota kill, a Ctrl-C, the non-zero-exit abort drawn above — ready-for-agent is left mid-rewrite on the tracker. That is why recovery is re-run the wave driver, not a bare dispatch-agents --prd: the driver rewrites the labels from scratch before every wave, and a bare orchestrator run would dispatch whatever the interrupted rewrite happened to leave behind. ADR 0045 records that the abort removal makes this trap rarer, not gone.

What happens when a wave fails

ADR 0045 · the change that matters most

There are two different failures here and they behave in opposite ways. Conflating them is the single easiest mistake to make about this file.

CARRIES ON  the wave came back incomplete

The orchestrator exited 0, but when the driver re-reads the tracker, at least one slice it dispatched is neither closed nor status:done. The wave and its slices are recorded in incompleteByWave, a warning is printed, and the loop continues to the next wave.

Aborting here is what turned an unattended PRD into a wasted night: wave 1 stalls, waves 2 and 3 never run, and nothing at all is integrated — twice, on gate faults unrelated to the code. Later waves may depend on this one and may well fail too; a failed wave that reports is still strictly more useful than a PRD that stopped. — .sandcastle/dispatch-waves.mts, on the continue

Be clear-eyed about the price. Wave 2 branches off a head that is missing wave 1's work, so a dependent wave can fail for a reason that has nothing to do with its own slice. That is accepted, not overlooked — nothing is pushed, git branch -f is reversible, and every slice branch survives.

HALT  the orchestrator itself exited non-zero

A different thing entirely, and the abort removal did not touch it. If the main.mts process returns a non-zero code, the driver calls fail() and the run ends on the spot: later waves do not run, the end-of-run gate does not run, and no summary is printed.

In practice the orchestrator returns 0 for the common overnight failures — a slice that crashed, a slice that was parked for quota — so the carry-on path is the one you will normally hit. A non-zero exit means the orchestrator itself could not proceed: bad arguments, a missing credential, an unresolvable feature branch.

Either way the tracker is mid-rewrite. Re-run the wave driver.

Why not abort, or gate per wave, or feed the failure back?
  1. Keep the abort. Rejected: the abort did not make failure visible, it made it total. Visibility is better served by a verdict comment on the PRD issue, which is legible in the morning.
  2. Gate once per wave. The strongest alternative, and rejected on cost: it triples gate spend to narrow a bisect that git log --oneline origin/main..feat/<slug> already makes cheap, and it still misses interactions between slices in different waves.
  3. Feed a red gate back to the agent. Rejected: every iteration is a cold sandbox at full price, and the failures that motivated the change were environmental — the agent would have burned a quota window “fixing” code that was never broken.
  4. Leave slices open until the gate is green. Rejected: a re-run would then re-dispatch slices whose commits are already in the feature branch. Skipping on status:done is what makes re-runs idempotent, so it has to key on something that is true.

Every wave defers; the driver gates once

--defer-gate · --gate-only

Because the driver invokes main.mts once per wave, “gate once at the end” cannot live inside main.mts alone. Two flags carry it:

--defer-gate
Passed to every wave. It suppresses the orchestrator's own end-of-run feature-branch gate, so a three-wave PRD does not gate three times.
--gate-only
Invoked once, after the last wave, as main.mts --prd <n> --gate-only. It launches no agent, so it needs no agent credential — which also makes it the way to re-check a branch by hand later.

The gate runs on origin/main...feat/<slug>: the same scope CI will run on the pull request, and the only scope that can see two slices breaking each other. It reports and does not block — by the time it runs there is nothing left to protect, because the slices are already integrated. What the gate actually executes, over which projects, and how the standalone mode differs is drawn on gates.html.

--prd and --plan are the driver's own flags; every other argument on the command line is forwarded verbatim to both the wave passes and the final gate pass. One exception: --fresh is refused outright, because it is a surgical instruction about one inspected attempt and a wave run spans every slice in the PRD. Discard the single slice with main.mts --prd <n> --issue <slice> --fresh, then re-run the waves.

The summary you read in the morning

end of dispatch-waves.mts

This block is the deliverable of an unattended run. Three lines, and each one answers a different question you will have before coffee. 

PRD #446 — run summary

  waves attempted   3
  incomplete waves  wave 1 (#101, #102)
  feature gate      FAIL

Nothing is pushed and nothing was discarded. Every slice branch is intact.
waves attempted
How many levels the plan produced. Not how many succeeded — a skipped, already-complete wave counts here too.
incomplete waves
none, or every recorded wave with the slice numbers that did not reach status:done. Start your triage here, at the lowest-numbered wave: later ones may have failed only because this one did.
feature gate
PASS or FAIL on the assembled branch. The same verdict is also a comment on the PRD issue, because terminal scrollback is gone by morning and the run may have finished hours earlier.

The process exits non-zero if the gate failed or any wave was incomplete — but only after everything has been integrated and reported. When both are clean, the closing message is the hand-off: QA the local feature branch, then git push -u origin <feature-branch> and open one pull request to main by hand. Re-running skips slices already marked status:done.

Slice list limits — what to check when work vanishes

gh issue list --limit

Three different gh issue list calls, three different caps. A slice past the cap is not reported as missing; it is simply never seen, which is what makes a truncated backlog look like a planning mistake.

waves 100
The wave driver's own query — type:afk, --state all, then filtered to this PRD. This is the list your waves are computed from.
PRD 100
The orchestrator's PRD query, also --state all, run again inside every wave pass.
sweep 200
The orchestrator's sweep query, --state open. It has nothing to do with waves — sweep explicitly excludes any issue carrying a PRD: #<n> reference — and is listed here only so the three caps are never confused for one.

Diagram notes

the same text every tooltip shows

Each entry is the note attached to the box of the same name. The tooltip reads its text out of this list rather than carrying a copy, so the two cannot drift — and a screenshot, a print, or a touch device loses nothing. Two boxes on the diagram carry no note, because they have nothing to add to what is already written on them.

gh issue list --label type:afk
--state all, not open. The orchestrator closes a slice when it integrates it, so a completed slice has to stay visible — otherwise a blocker that already shipped would look unsatisfiable and a re-run could not tell a finished wave from a missing one. The repository is hard-coded to mnaimfaizy/myorganizer.
fetchSlices()
The label query is not enough on its own: it returns every type:afk issue in the repository. What makes a slice yours is the literal string PRD: #<n> in its body. A slice whose body lost that line is invisible to the driver and will never be dispatched.
blockersOf()
The heading is matched case-insensitively and the section runs to the next ## heading or the end of the body. Every #<number> inside it is a candidate edge, then two are dropped: a reference to an issue that is not a slice of this PRD, and a self-reference. So a slice blocked only by outside work has no blockers as far as the driver is concerned.
computeWaves()
Kahn's algorithm taken level by level, not one node at a time: every slice whose blockers are all resolved joins the same wave. Ordering within a wave is by ascending issue number, but that is cosmetic — the orchestrator dispatches a wave's slices one by one and each sees the work of the earlier ones, so a wave is a set, not a promise of independence.
Dependency cycle → fail()
When a level resolves to zero slices while slices remain, the driver names every remaining slice and exits. There is no partial run: the cycle is a planning error in the issue bodies, and the fix is to edit a ## Blocked by section, not to re-run.
--plan → exit 0
The safe way to check your ordering. It prints the same wave plan the real run prints, then exits before the first label write — so a preview cannot alter the tracker. Slices already finished are marked (done) in the plan.
Re-read the slices
The full query runs again at the top of every wave, not once. That is what lets a re-run pick up work you closed by hand between runs, and what lets a wave notice that a prior wave finished slices it was waiting on.
openInWave
A slice counts as complete if its state is CLOSED or it carries status:done. Since ADR 0045, status:done means integrated, not verified — the gate no longer runs per slice, so a done slice is one whose commits are in the feature branch, nothing more.
Already complete → skip
Nothing at all happens for a finished wave: no labels are rewritten and no orchestrator pass is spawned. This is what makes re-running the driver cheap after a partial night, and it keys on the same isDone test as everything else.
ADD ready-for-agent
One gh issue edit per slice that needs it — the driver checks the current labels first and writes nothing when the state is already right, so a re-run of an in-flight wave is quiet. This is the write that causes dispatch: the orchestrator picks up open + ready-for-agent + type:afk.
REMOVE ready-for-agent
The half people forget. It strips the label from every other slice of the PRD — future waves, so they cannot run early; and already-done slices, so they cannot run twice. Without it the orchestrator's filter would happily re-dispatch work that is already in the branch.
Run the orchestrator
A child process with stdio: 'inherit', so the orchestrator's output is the driver's output — there is no separate wave log to find. It handles the whole slice lifecycle: branch, container, agent, fast-forward, writeback. --defer-gate is added by the driver; --prd and --plan are stripped and every other flag you typed is forwarded.
Exit code ≠ 0 → fail()
The one place the driver still stops. ADR 0045 removed the abort on an incomplete wave, not the abort on an orchestrator that could not run at all — bad arguments, a missing credential, an unresolvable branch. No later wave runs, no gate runs, and no summary is printed, so this failure looks different from every other one.
Re-read; verify isDone()
A third read of the tracker, after the wave. The driver does not trust its own bookkeeping here: the orchestrator is the thing that closes slices and applies status:done, so the tracker is the only honest answer to “did this wave finish?”
incompleteByWave.push(…)
The behaviour ADR 0045 changed. The wave number and its unfinished slices are recorded, a warning naming them is printed, and the loop continues. The warning says so explicitly: later waves that depend on these may fail too, and everything is reported at the end. A PRD that runs to the end and reports beats one that stopped at wave 1.
Gate once, at the end
--gate-only re-invokes the orchestrator purely to gate the assembled feature branch against origin/main. It launches no agent and therefore needs no agent credential, which makes it the supported way to re-check a branch by hand days later.
Comment the verdict
The third and last GitHub write of the driver's run. A red verdict spells out that every slice is still integrated and every slice branch intact, and hands you the bisect: git log --oneline origin/main..feat/<slug>. It is a comment rather than a label because it has to reach a phone.
The run summary
Written whether the run went well or badly — unless the orchestrator exited non-zero, which ends the process before this point. If you have a summary at all, every wave was attempted.
Exit code
Non-zero when the gate failed or any wave was incomplete, so a wrapper script can still tell a bad night from a good one. The difference from the old behaviour is when: the code is computed after everything has been integrated and reported, not instead of it.
Nothing pushed, nothing discarded
True on every path out of this file, including the failures. No git push, no pull request, no branch deletion, and no checkpoint destroyed — --fresh is refused by the wave driver outright. What you have in the morning is a local branch and a set of intact slice branches.
