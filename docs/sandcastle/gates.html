One runGate. Two callers that disagree about what a red verdict is allowed to do.

A red PRD gate did not block anything

In standalone mode the gate is fail-closed: red means the work was not handed back as done. In PRD mode the gate runs after every slice has already been fast-forwarded into the feature branch, so red is a report — the code is already on the branch, the slices are already closed, and nothing was discarded. ADR 0045 inverted ADR 0010's fail-closed guarantee deliberately, for PRD mode only. That is the first thing to establish when you read a failure.

The reading test — scope

If your change touches only a lib's internals, lint runs on that lib and test runs on every consumer. A green local nx test <lib> is not the gate: it never compiled or ran the suites of the projects that import your lib, and those are exactly the ones a lib change breaks.

Two scopes, because the targets have different blast radii

main.mts:153, 205, 1642-1687

The default target list is lint test build, and it is split in two before anything runs. lint is per-file: an upstream change cannot introduce a lint error in an unchanged downstream file, so it runs only over projects whose own files changed. Everything else is cross-project — a lib change routinely breaks an unchanged consumer's compile or suite — so it runs over the affected set: changed projects plus their transitive dependents.

  • Each scope becomes exactly one nx run-many inside the container, and a scope that resolves to no projects is dropped rather than run empty.
  • affectedProjects() shells out to nx show projects --affected with an explicit --json, capped at 300000 ms (5 minutes). The flag is explicit because Nx auto-enables JSON only when its isAiAgent() probe fires on CLAUDECODE and friends — from a plain terminal the identical command printed a newline-delimited list, JSON.parse threw, and every slice failed the gate on an unresolvable graph.
  • Unresolvable means false FAIL-CLOSED. The function returns null and logs the real reason; the caller only knows that resolution failed.
  • changedProjects() diffs a three-dot range, so a slice is compared against its merge-base rather than against a base that has moved on underneath it. affectedProjects() hands the same two refs to Nx as --base and --head and lets Nx resolve the graph.

One honest gap, worth knowing when the gate is green and CI is not: CI lints wider than the gate does. The workflow runs nx affected -t lint and nx affected -t test, so CI lints the affected set while the gate lints only the changed set. Per-file rules cannot tell the difference — @nx/enforce-module-boundaries can, because retagging a lib can make an unchanged consumer's import illegal in a file the gate never looked at.

What PRD mode gives up, stated plainly

ADR 0045 inverts ADR 0010's fail-closed guarantee for PRD mode on purpose, and it costs two real things.

The feature branch can contain unverified code, and a broken slice can compound into every later slice that was cut from it. Per-slice attribution is lost: a red feature gate says the branch is broken, not which slice broke it. The bisect is the ordered slice commits — git log --oneline origin/main..feat/<slug> — and every slice branch survives intact for re-gating by hand.

It was accepted because nothing is pushed, git branch -f is reversible, and human QA before the PR was always the real gate for a local branch. It also weakens status:done from “verified and integrated” to “integrated”.

The alternative that was closest, and why it lost
  1. Gate once per wave. Three gates instead of six or one, attribution narrowed to a wave, a broken wave caught before the next stacks on it. Rejected on cost against benefit: it triples the gate spend to narrow a bisect that git log --oneline already makes cheap, and it still misses interactions between slices in different waves. Worth revisiting if PRDs grow long enough that a full-branch bisect stops being trivial.
  2. Keep per-slice gates but make them non-blocking. Preserves attribution, but keeps all N installs and still cannot see cross-slice breakage. Retained in spirit: when a per-slice gate does run, its verdict still reaches the slice log as a HANDOFF: marker.
  3. Feed a failed gate back to the agent. Rejected: every iteration is a cold sandbox with a fresh install at full price, and both real failures that motivated the change were environmental — the agent would have burned a quota window “fixing” code that was never broken.

Reading a red gate

main.mts:1101-1115, 2891-2913
  1. Establish the mode first. A verdict labelled [#123] came from a standalone slice gate and blocked something. A verdict labelled with a branch name came from runFeatureGate and blocked nothing.
  2. Read the gate output in the run log, not the exception. The container runs with inherited stdio, so the Nx failure is in the run log verbatim.
  3. Find the slice. git log --oneline origin/main..feat/<slug>. Slices are committed in order, so this is the bisect list. Nothing was discarded: every slice branch still exists.
  4. Re-check the branch by hand with yarn dispatch-agents --prd <n> --gate-only. It launches no agent, so it needs no agent credential — which matters, because it is the path you run on a machine where the 1Password injection was never set up. It gates the feature branch and exits with the verdict's status.
  5. There is no per-slice re-gate flag. The slice branches survive for individual re-gating, but nothing in the orchestrator will do it for you — that is a manual nx run-many.
The trap: SLICE_GATE=off makes --gate-only lie

SLICE_GATE is checked as the very first statement of runGate, before targets, before scopes, before the container. With off left in .sandcastle/.env, a --gate-only run prints PASS, comments passed on the PRD issue, and exits 0 without resolving a single project. The log line “gate disabled — integrating without verification” is the only tell.

Two different things are called a gate

main.mts:1925 · ADR 0012

Everything above is the build gate: a host-side, deterministic check in a container. It shares a word with the quality gate tier, which is a label on the issue and never runs anything. Confusing the two is how a gate:mechanical slice ends up believed to be exempt from lint test build. It is not.

Build gate Quality gate tier
Where Host → Docker → Nx Inside the agent's prompt
Set by SLICE_GATE_TARGETS, defaulting to lint test build resolveGate(issue) reads the issue labels: gate:mechanical, gate:full, and otherwise standard

The tier is resolved once, when the prompt is built, and an issue with no gate:* label gets standard. It changes what the agent is told to do; it changes nothing about what the host runs afterwards.

The same text every tooltip shows

Each entry is the note attached to the box of the same name. The tooltip reads its text out of this list rather than carrying a copy, so the two cannot drift — and a screenshot, a print, or a touch device loses nothing.

SLICE_GATE = off ?
The first statement in runGate, before targets, before scopes, before any container. It returns true and logs “gate disabled (SLICE_GATE=off) — integrating without verification”. Because it is first, it also silently satisfies --gate-only: a feature branch can be reported passed on the PRD issue without a single project being resolved.
changedProjects()
Maps the files in base...head to the project rooted at each file's nearest ancestor project.json. That deliberately excludes transitive dependents: a change to vault-core returns vault-core and nothing else. Correct for lint, which is per-file, and wrong for everything else. If it returns an empty list the gate passes immediately — no worktree, no container.
affectedProjects()
nx show projects --affected --json, run on the host and capped at 300000 ms. It has to be the host: the gate bind-mounts only the worktree directory, and a linked worktree's .git is a file pointing at the parent repo, so git cannot resolve refs inside the container. The --json is explicit because Nx auto-enables it only when its isAiAgent() probe sees CLAUDECODE. Returns null on any failure, and the caller then fails closed rather than gate a narrower set than intended.
git worktree add --detach
A dedicated worktree at .sandcastle/gate/<branch>, with slashes in the branch name flattened to dashes. Detached and on its own path so it never holds the slice branch checked out, and so it does not depend on the agent's worktree still existing — by gate time that one may already have been removed. It is pruned and force-removed before creation and again in a finally. A failure to create it fails closed.
docker run
A second container, separate from the agent's, running as the host UID:GID with the gate worktree and the shared Yarn cache bind-mounted. It installs the slice's exact tree (corepack yarn install --immutable) so a lock-changing slice is validated with container-matching binaries, then runs one nx run-many ... --skip-nx-cache per scope, chained with &&. The Nx daemon and Nx cache are off. Timeout 3600000 ms (3,600,000 ms — 60 minutes), raised from 30 when build joined the target list.
The verdict — one boolean
runGate returns a boolean and prints gate: PASS or gate: FAIL against the run label. It also mirrors the verdict into the slice log as a HANDOFF: marker — gate PASS (lint test build) or gate FAILED (lint test build) — but only when a caller passes an issue number, and only runSliceGate does. A feature-branch gate writes no handoff marker, because it is a fact about the assembly rather than about any one slice. See logs.html and resume.html.
RED — the gate BLOCKS
Standalone only. A false verdict sets mergeOk false, so nothing is handed back as done: status:in-progress is removed, a comment says the build gate (lint test build) failed and names the branch left in place, and the issue stays open and un-status:done. There is no integration branch in this mode, so there is no later gate to defer to — which is exactly why this one is allowed to block.
NO GATE HERE
In PRD mode the value fed to the integration step is not a gate verdict at all: it is hasWork, which asks only whether the slice produced commits. Any slice that did fast-forwards into the local feature branch and is closed status:done. status:done therefore means integrated, not verified — and that is what keeps a re-run idempotent, because the skip has to key on something that is actually true.
--defer-gate × every wave, then --gate-only once
The wave driver invokes main.mts once per wave, so “gate once at the end” cannot live inside main.mts alone. Every wave is passed --defer-gate, which suppresses the end-of-run gate; after the last wave the driver re-invokes with --gate-only, which runs the feature-branch gate and exits. A direct --prd run with no driver gates at the end of its own run, which for one invocation is the same thing. --gate-only requires no agent credential, because it launches no agent. See waves.html.
runFeatureGate(feat/<slug>)
Gates origin/main...feat/<slug> — falling back to main if origin/main does not resolve locally. baseRef cannot serve here: in PRD mode it is the feature branch, which advances with every integrated slice, so diffing against it would show the last slice only.
reportFeatureGate
The verdict is posted as a comment on the PRD issue, not only to the terminal: scrollback is gone by morning and the run may have ended hours ago, so the issue comment is the notification that reaches a phone. A failing comment states that every slice is still integrated, every slice branch intact, nothing discarded and nothing pushed, and hands over git log --oneline origin/main..feat/<slug> as the bisect. Slices stay closed either way.
