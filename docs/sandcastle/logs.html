Evidence

A slice failed overnight. Two independent trails were written while it ran, and only one of them is summarised for you. This page says where each lives, what is in it, what is missing unless you asked for it — and which of those two sentences is actually true about --trace-subagents.

Both trails are files under .sandcastle/ on the machine that ran the dispatch. Nothing is sent anywhere.

The one thing to get right about this flag

--trace-subagents does not decide whether sub-agent transcripts are captured. Sandcastle 0.12.0's Claude Code provider captures every one of them to the host automatically and unconditionally, as part of ordinary session capture. The flag decides one thing only: whether main.mts relocates and summarises them into .sandcastle/logs/subagents/<issue>/index.md.

Read the flag as "capture" and you will conclude that a run without it produced no sub-agent evidence, and stop looking. It produced all of it.

The slice log file
Written by sandcastle's own file display, into .sandcastle/logs/. The run is named #<issue>, which is where the doubled dash in <branch>--<issue>.log comes from — e.g. slice-447-resume-brief--447.log. The orchestrator never reconstructs that name; it matches the --<issueNumber>.log suffix, so a renamed branch does not lose the file. It is opened with an append flag, so a re-dispatch adds to the existing file rather than replacing it.
--- Run started: segments
Because the file is appended to, the only thing separating one run from the next is the marker --- Run started: that sandcastle writes as it opens the log. Everything downstream slices on the last occurrence. That is not a nicety: a plain tail-of-file once reached back past a run boundary, read the previous run's usage-limit message as this run's ending, and parked a dispatch for roughly twenty hours over what was actually a dependency-install failure.
sliceLogPathFor()
Lists .sandcastle/logs/, keeps the names ending --<issueNumber>.log, and sorts by mtime — newest wins. If the directory does not exist, or nothing matches, it returns nothing and every reader of the log degrades quietly rather than failing the dispatch.
readSliceLogTail()
The last 15 non-empty lines of the current run segment, printed next to the crash. The reason is in the source: the thrown AgentError carries whatever was last on stderr, "which is routinely a trailing warning rather than the cause." The tail is offered as context, not as a diagnosis — the orchestrator deliberately does not classify it here.
extractHandoff()
The second reader of the same file. It takes only lines carrying the HANDOFF: marker, from the last run segment only, de-duplicates them (a marker echoed by the agent and logged by the orchestrator is one event), and caps how many travel. Raw log tail is excluded on purpose: it would drag a dead agent's mid-thought reasoning into the next brief as if it were instruction.
The next run's resume brief
This is where the two pages join. Git records the files a run produced; nothing in git records which pipelines ran or why the run ended, so the slice log is the carrier for that — chosen precisely because it always exists, where logs/subagents/<n>/index.md may simply not be there. What the next agent is told, and why an absent handoff must read as unknown rather than "nothing ran", is resume.html.
The orchestrator writes into the same log
Markers are not only the agent's. When the gate finishes, the orchestrator appends its own verdict as a HANDOFF: line — gate PASS (lint test build), or a gate FAILED line that says in words that the work was committed and the host gate rejected it. That is the one thing about the previous run git cannot show the next agent, and without it a resumed agent cannot tell "my code was rejected" from "I was killed mid-thought". Writing it is silent on failure: a missing log must never take down a dispatch.
What one flat log cannot say
The failure that produced trail 2. Slice #397 integrated with a green gate while two of its checks had never run: a sub-agent typechecked the wrong tsconfig and invoked a lint target that does not exist. In the flat log its commands were a single line among 3,314, typographically identical to the orchestrator's, with no marker for where that sub-agent's work started or ended. See ADR 0036.
Claude Code writes one file per sub-agent
Not a stream to be split. Claude Code writes each sub-agent invocation to its own file, <sessionId>/subagents/agent-<agentId>.jsonl, sibling to the main session transcript. The boundary problem ADR 0036 set out to solve was already solved at the filesystem level, which is why nothing here infers one.
Attribution is already in the file
Every assistant turn carries attributionAgent and attributionSkill, set by the harness, plus its own full usage block. That is what makes the summary derivable rather than guessed. One real gap: sandcastle's capture matches only agent-*.jsonl, so the .meta.json sidecar is lost on an AFK dispatch — not load-bearing, because the same agent and skill names are duplicated onto every turn.
Live, through the sessions mount
.sandcastle/sessions on the host is bind-mounted at /home/agent/.claude/projects in the sandbox, so the transcripts are on your disk as they are written, not only at the end. That is what makes recovery possible after a crash, where there is no RunResult and no session id to look up: the orchestrator walks that directory and takes everything modified since the run began.
captureToHost()
Sandcastle 0.12.0's Claude Code provider enumerates <sessionId>/subagents/agent-*.jsonl inside the sandbox and copies each one to <hostProjectsDir>/<encodedCwd>/<sessionId>/subagents/ on the host. This happens as part of ordinary session capture, with no flag of ours involved. It is the single most misread fact on this page. One correction to the repo's own wording: the copy is not quite byte-for-byte — the shared copy helper rewrites the cwd field on each record from the sandbox path to the host path. Nothing else in the transcript is touched, and a copy that fails is logged and skipped rather than failing the run.
--trace-subagents
Everything above this box happens whether or not you pass it. The flag gates one thing: whether main.mts relocates the already-captured transcripts under .sandcastle/logs/subagents/<issue>/ and writes index.md. It was made opt-in deliberately — the flat log is what a human actually opens when a run fails, and a second always-present artifact invites "which one do I read?" on every failure. The cost was weighed and accepted: a flag cannot be switched on retroactively for a run that has already failed. On a run with more than one iteration the copies are prefixed iteration-<index>--, so two cold restarts do not overwrite each other.
No index.md
Without the flag, output is byte-for-byte what it is today: one flat log per slice, and nothing under logs/subagents/. This is an absence of summary, not an absence of evidence. A slice that spawned no sub-agents writes nothing there either way, so an empty directory does not distinguish the two — check whether the flag was passed.
Relocate and summarise
Each captured transcript is copied verbatim into .sandcastle/logs/subagents/<issue>/ next to the index, so the raw file is one directory away from the summary of it. Nothing is rewritten or filtered on the way.
index.md
Markdown, so it opens readably next to the raw transcripts with no special tooling. Its heading names the issue and the slice branch, then it states how many sub-agent invocations were captured, then one section per sub-agent titled with its agent type and skill.
Seven lines per sub-agent
Transcript filename, model, turns, peak context, token usage, tool calls with counts, and MCP servers. Two of those lines are worded the way they are on purpose. Token usage is summed per-turn snapshots, not a single total — the line says so in its own label, and peak context is the largest single-turn input + cache-write + cache-read, which is the number that tells you how close that sub-agent came to a context limit. And "MCP servers: none invoked" is printed even when the list is empty, because a silent absence reads as "no MCP was needed" when the more common cause is a configured server that never started in the sandbox.
A missing index.md
The reading test for this page. The transcripts are still on the host under .sandcastle/sessions/, in the session directory for that run. You did not lose the evidence — you skipped the summary, and you can still read the raw agent-*.jsonl by hand.

All four are gitignored by .sandcastle/.gitignore (logs/ and sessions/), so nothing here can be swept into a slice commit and nothing leaves the machine. Setup and recovery procedure — how to actually run a dispatch with the flag — stay in the sandcastle RUNBOOK.

What one index.md entry says

tools/scripts/lib/sandcastle-subagent-trace.mjs · formatSubagentIndex 
# Sub-agent trace — #447 (slice/447-resume-brief)

1 sub-agent invocation(s) captured.

## TestReviewer — unit-test-delegation-workflow

- Transcript: `agent-abc.jsonl`
- Model: claude-sonnet-5
- Turns: 12
- Peak context: 181k tokens
- Token usage (summed per-turn snapshots, not a single total): input 3.5k, cache-write 205k, cache-read 1.7m, output 41k
- Tool calls: Bash (9), Read (4)
- MCP servers: none invoked

Rendered by calling formatSubagentIndex directly, not transcribed. The heading names the issue and the slice branch; the section heading is the sub-agent's attributionAgent and attributionSkill.

Honesty detail 1 — the usage line

Token usage is summed per-turn snapshots, not a single total. The label says so inside the line itself, because the number looks exactly like a run total and is not one. Cache-read in particular accumulates across turns and will dwarf everything else.

Peak context is the different number worth having: the largest single-turn input + cache-write + cache-read observed. It is a proxy for how close that sub-agent came to a context limit — the summed figure cannot tell you that.

Honesty detail 2 — the empty MCP line

- MCP servers: none invoked is printed even when the list is empty. Dropping the line would be tidier and would mislead: a silent absence reads as "no MCP was needed", when the more common cause is a configured server that never started in the sandbox. Only an always-present line makes that visible.

The server names are derived from the tool calls themselves (mcp__<server>__<tool>), so the list cannot claim a server that was configured but never actually reached.

formatTokens — why 205k is not 204.8k
Input Rendered Why
1000 1k Below 10 units, so one decimal — and a trailing .0 is stripped.
1500000 1.5m Below 10 units, so the fraction is kept and means something.
204800 205k At or above 10 units the value is rounded to whole units, so the index never pads a false 204.8k precision nobody acts on.

Counts in one table run from thousands to millions — one real sub-agent's cache-read was 1702754 on one line and its input 3466 on the next. Raw digits at that spread are unreadable and, worse, hard to compare at a glance, which is the one thing the index exists for.

What you get when a slice dies

.sandcastle/main.mts:1437, 2228, 2790
The tail, and why it is only context

The crash handler prints the last 15 lines of the current run segment beside the error, prefixed with a warning that the error may not be the cause at all:

The thrown AgentError carries whatever was last on stderr, "which is routinely a trailing warning rather than the cause." Surface the log tail next to it instead of classifying it.

Scoping that tail to the current run is load-bearing, not tidiness — see the twenty-hour misfire in the note on run segments.

Transcripts survive the crash too

A crashed run has no RunResult, so there is no session id to look up and sandcastle never reached its own capture step. The transcripts are still there, because the container was writing them straight onto the host through the sessions mount.

With --trace-subagents, recovery walks .sandcastle/sessions and takes every agent-*.jsonl modified since this run started — selection by modification time, not by id. Dispatch runs one slice at a time against a per-repo store, so a stale directory from an earlier slice cannot qualify; the worst case is recovering nothing rather than the wrong thing.

The reading test

If index.md is missing, the transcripts still exist on the host. You did not lose the evidence — you only skipped the summary. Go to .sandcastle/sessions/…/subagents/ and read the agent-*.jsonl directly, or re-run the slice with the flag if you would rather have the summary next time.
