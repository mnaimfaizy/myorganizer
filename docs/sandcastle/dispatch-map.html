Sandcastle is not CI

CI runs once, on the unit that actually ships, after a human pushes. Sandcastle is the deliberate inverse: it runs before that, on work nobody has reviewed, and it stops at the push. Nothing it does reaches origin — the feature branch is created locally and never pushed. Deleting that local branch destroys the entire batch.

The three ownership zones

GitHub

Issue bodies, labels, comments, open/closed state. Read for the brief. Written only as labels, comments, and a slice close.

Host

All git: branch creation, worktrees, checkpoints, tags, the fast-forward, the local feature branch. Also the Nx affected-graph resolution.

Container

The agent, the install, the gate run. Credential-less for git; disposable; its filesystem does not survive.

The reading test — GitHub

If your change adds an arrow leaving the Host zone toward GitHub, it may only be one of four things: read an issue, add or remove an Issue Orchestration Label, post a comment, or close a slice. A push, a PR, or a merge from inside a dispatch is a violation of ADR 0010.

And for the other boundary: if your change adds an arrow entering the Container zone, say which of the four mounts or the one credential it travels on. There is no fifth channel.

Text version of this diagram
  1. Run setup. --help, argument validation, and mode resolution; then Claude credential resolution; then, and only then, ensureSandboxImage(). Building the image takes minutes, so nothing pays for it before the run is known to authenticate, and --dry-run never builds it at all. Then git fetch origin main and the run plan. PRD mode prints the plan unprompted; sweep mode prints it and blocks on y/N, failing rather than proceeding on a non-TTY; --dry-run prints it and exits with no worktree, no container, and no GitHub write. type:hitl and status:blocked issues are filtered out at selection and never enter the pipeline.
  2. Per slice, success. Add status:in-progress. Decide the disposition — resume, fresh, or skip-stale. Read maintainer notes from the issue's comments. Build the prompt. Create or reuse the worktree. Start the container, which installs dependencies before the agent wakes, then runs the agent. Log usage and capture sub-agent traces. finalizeSliceBranch sweeps up anything left uncommitted and fails a branch that is zero commits ahead. runSliceGate validates it in a second container. integrateSlice fast-forwards the un-checked-out feature ref. Write back to GitHub — which differs by mode — and clear status:blocked from dependents. The run ends without pushing anything.
  3. Per slice, interruption. Remove status:in-progress. Commit the dirty worktree as a Slice Checkpoint with --no-verify and tag it wip/<issue>-checkpoint. Recover sub-agent transcripts from the bind-mounted session store. Print the log tail next to the thrown error. Classify the failure and decide the wait policy. Then either park and re-queue the slice, or comment the checkpoint onto the issue and move on. The next dispatch resumes from the checkpoint unless --fresh is typed by hand.

The asymmetry is the point

PRD slices close because their work is integrated. Standalone runs stay open because marking them done would assert completion of work that exists only on an unpushed local branch.

Issue-list caps, in case a large backlog looks truncated: PRD mode fetches 100 (--state all), sweep fetches 200 (--state open), the wave driver fetches 100.

The gate — two scopes, one run

main.mts:150-222, 1473-1617

This is the mechanism that makes “AFK” defensible. Default targets are lint test build, and they do not run over the same set of projects.

  • Runs in a dedicated detached worktree under .sandcastle/gate/<branch-with-dashes>, removed in a finally. Detached and separate so it never holds the slice branch checked out and does not depend on the agent's worktree still existing.
  • Runs in a second Docker container as the host UID/GID, which installs the slice's exact tree (corepack yarn install --immutable) and then runs Nx. The resolved project list is passed in as an explicit --projects=.
  • Fails closed everywhere FAIL-CLOSED: unreadable project graph, gate worktree creation failure, non-zero container exit.
  • Defaults: SLICE_GATE_TARGETS = "lint test build"; container timeout 3,600,000 ms (60 min); SLICE_GATE=off skips the gate entirely and integrates unverified.
  • build is what typechecks this repo — there is no typecheck target — and the default set mirrors what CI will run on the eventual PR, so a gate-green slice is not one that fails the moment it is pushed.

Interruption and resume

tools/scripts/lib/sandcastle-resume.mjs
decideSliceDisposition — in evaluation order
  1. --fresh given → fresh. Outranks everything; the only path that destroys work DESTROYS.
  2. Branch missing, or 0 commits ahead → fresh.
  3. merge-base(slice, base) ≠ base → skip-stale. Reported and skipped, branch left intact. Not rebased, not deleted — slices stack, so a checkpoint stranded while later slices integrated is based on a head that is no longer in history. Rebasing is a human judgement call.
  4. Otherwise → resume.

On resume the branch and its commits are kept; only the worktree is rebuilt, so the agent gets a clean checkout of the checkpoint rather than the interrupted container's partial disk state.

The resume brief prepends six guardrails — two carry the safety argument
Files present in the checkpoint do NOT satisfy a Gated Pipeline. A spec file already in the tree does not mean TestScaffold ran, was reviewed, or passed.
Nothing in the checkpoint has passed a deterministic check. It was committed with --no-verify while the run was being killed, so lint, tsc and the test suite have never once seen it.

The checkpoint diff is deliberately not inlined into the prompt: the agent reads it from git in one command, and inlining spends the context that resuming exists to conserve.

Maintainer notes only travel under one heading

Only text under a ## Maintainer Review heading in an issue comment reaches the next agent's prompt. Issue #396 was dispatched three times with three reviewed findings sitting unread in ordinary comments.

--fresh — three different answers to the same flag
Standalone allowed
PRD must name its slice: --prd <n> --issue <slice> --fresh
Sweep refused — a blanket discard over a set nobody named
dispatch-waves refused outright, not forwarded — a wave run spans the whole PRD

Per-slice output lands in .sandcastle/logs/<…>--<issue>.log, one flat file per slice, appended across re-dispatches.

Quota waiting — five refusals and one wait

sandcastle-resume.mjs:316-527

Quota exhaustion is the expected outcome of an overnight PRD, not an edge case (ADR 0035). Every branch below is a deliberate refusal; “wait” is reached only through all five.

  1. --wait-for-quota was passed. Opt-in — a run that goes silent for hours is a severe surprise.
  2. The classification is limit-hit, not other and not unknown.
  3. The reset time parsed. Only resets [at] H[:MM](am|pm) (UTC) is accepted; a bare local time is ambiguous across machines. FAIL-CLOSED
  4. Fewer than 2 waits already taken this run.
  5. The reset is within 6 hours. Further out is treated as untrustworthy.
  6. Sleep until the reset plus a 5-minute margin, then re-queue the slice so the next pass finds the checkpoint and resumes rather than restarting.
Ignorance is modelled, not papered over

Classification is provider-keyed. Claude Code has 3 observed matchers; cursor and copilot have 0 and therefore classify as unknown, never other. The difference is “we did not look” versus “we looked and it was not a limit” — and only the second could ever justify a wait.

Why the tail scan is run-scoped

The scan reads only the current run in the slice log, split on the marker --- Run started:. Slice logs are appended across re-dispatches; a plain tail-of-file once read a previous run's limit message and parked a run for roughly twenty hours.

Cost note for a subscription-auth sweep: subscription auth shares the same 5-hour window as interactive Claude Code, and complexity:high routes to claude-opus-5. An overnight sweep can throttle your own keyboard.

Exactly one Claude credential is forwarded

The OAuth token wins when both are present, and ANTHROPIC_API_KEY is then not forwarded at all — because which one Claude Code prefers is version-dependent, and a stale key next to a valid token would silently bill the API while you believe you are on the plan. SANDCASTLE_CLAUDE_AUTH forces a mode and fails before any worktree or container is built.

Pointedly not mounted

The host's ~/.claude/.credentials.json. The container would write token refreshes back into the host credential store, and the file does not exist on macOS at all. claude setup-token is the supported headless path.

The image lifts some guards and keeps others

MYORGANIZER_SANDBOX=1 is baked into the image. The shared pre-tool-use.mjs hook reads it and lifts the workflow guards on generated paths — API client, synced spec, generated Swagger, generated design tokens, Prisma migrations — because in a disposable container they block legitimate work. In issue #408 they rejected every git restore the agent tried after a botched regeneration, so it committed a deletion it could not undo.

Secret guards stay active. The container's filesystem is disposable, but the transcript is not — it lands in .sandcastle/logs/ on the host and is fed back into model context.

  • The image pre-accepts the workspace trust dialog. Without it Claude Code refuses to load the repo's .claude/settings.json allowlist, and that warning becomes the last thing on stderr and gets misreported as the agent error.
  • The image ships a JRE, because openapi-generator-cli is a Java tool and java: not found once made issue #408 unfixable in the sandbox.
The one environment fact that belongs here

The worktree must live on a native filesystem (ext4, APFS). Same install: ~2m04s on ext4, ~29m on a Windows drvfs mount (ADR 0009). Its violation looks like a hang, not an error — which is why it is a correctness property and not a setup tip. Everything else about setting the machine up lives in the RUNBOOK.

A rule that describes a frequency is not a rule

The earlier wording described how often to run /code-review without ever telling the agent to run it — satisfiable by never invoking it, which is exactly what happened.

The prompt names sub-agent pipelines — TestScaffold → TestReviewer → TestRunner, ComponentBuilder → ComponentReviewer, E2EPlanner → …. This page deliberately does not redraw that fleet; it is drawn in orchestration-map.html and skill-atlas.html.

Waves add exactly one thing: ordering

.sandcastle/dispatch-waves.mts:111-297

dispatch-waves.mts topologically sorts the PRD's type:afk slices by their ## Blocked by sections into Kahn levels, then runs one main.mts --prd pass per wave, gating each wave by rewriting ready-for-agent across every slice in the PRD.

The trap that bites during recovery

The driver aborts the moment a wave does not fully reach done, and it does not restore those labels on the way out. A plain dispatch-agents --prd <n> afterwards therefore sees only the aborted wave and silently skips every later one. Recovery is re-running the driver.

Not restoring the labels is itself a decision: a failure path that mutates several issues on the way out can half-complete and leave the tracker worse than it found it (ADR 0035).
